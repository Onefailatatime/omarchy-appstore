splinterm-mcp on Omarchy

splinterm-mcp is a policy-scoped MCP adapter for Splinterm that lets your coding agents (Claude Code, Codex, VS Code) reach your persistent terminal sessions through a bounded, consent-gated interface instead of raw shell access.

TL;DR

omarchy pkg add splinterm
omarchy pkg add splinterm-mcp

Install splinterm-mcp on Omarchy with one command. It takes ~2 minutes. MIT-licensed open source, free, no paid tier. Guide drafted against the 0.1.1-1 Omarchy package (store listing reports 1.9 MB download / 5.3 MB installed).

You need both: the adapter is a separately packaged split of Splinterm's automation surface, and it operates on the same splinterd-owned sessions. Installing the package or adding it to an agent host grants nothing — every operation is denied until you explicitly grant access.

Getting started (5 minutes)

1. Install both packages.

The adapter without Splinterm is useless; install splinterm first if you haven't.

2. Add the adapter to your agent host in one command.

splinterm mcp setup claude-code    # or: codex, vscode
splinterm mcp setup codex --dry-run   # preview the change first

This adds one MCP server named splinterm to the host's config and changes nothing else: Claude Code gets an entry in ~/.claude.json, Codex in ~/.codex/config.toml, VS Code in ~/.config/Code/User/mcp.json. Setup grants no access and writes no policy. Start a new session of the host to load the server.

3. Grant access when (and only when) the agent asks.

The first time the agent needs a workspace, it calls request_lair_access and you answer in Splinterm's prompt — a default-deny trusted prompt with three access levels (Look, Look and type, Manage) and three durations (just this once, while this workspace is open, always for this workspace). Grants for a protected package install can be remembered; development builds are only offered the two shorter durations.

4. Watch what agents are doing.

Agents self-report status (working, needs_input, done, error, idle) through splinterm report_agent_status or the MCP tool splinterm.report_agent_status; the Explorer shows a per-Splint icon and per-Dojo tab badge, and the command palette lists pending agent access requests with per-entry revoke. See herdr if you want a dedicated agent-watcher on Omarchy.

5. Revoke when done.

splinterm access list shows the adapter's grants; splinterm access revoke ends them. Removing the splinterm entry from your host config (splinterm mcp remove claude-code) does NOT revoke grants — revoking is separate and deliberate.

Common issues & fixes

All sourced from the project's own MCP docs and status doc. Nothing below was reproduced on Omarchy — confirm each fix on-machine before relying on it.

An agent's request to reach a workspace silently fails or is denied

Fix: Denial is the default. Machine clients never inherit human graphical authority, and the daemon denies every adapter operation until you grant the exact executable path and digest policy. Check splinterm access list for the grant and answer the pending request in Splinterm's prompt — a waiting indicator (Explorer mark, window title, palette count) shows requests awaiting an answer. (docs/mcp.md, docs/status.md)

splinterm mcp setup refuses to write your host config with a refusal naming permissions

Fix: Setup is paranoid about the files it edits: it refuses malformed JSON/TOML, symlinks, files owned by another user or group-writable, and private-group setups (umask 002) that make files 0664. Run the exact chmod g-w command the refusal names, then retry. A shared sticky directory like /tmp is refused outright. (docs/mcp.md)

Setup added the server, but Claude Code doesn't see the splinterm MCP server

Fix: Start a NEW session of the host to load the server. Also: Claude Code rewrites ~/.claude.json while running, so a session that was open during setup can write its older copy back — run setup with no Claude Code session open, or verify afterwards with claude mcp get splinterm. (docs/mcp.md)

VS Code mcp.json entry doesn't behave as expected

Fix: Upstream is honest about this one: the VS Code entry follows the documented form but was not verified against a real VS Code install. If setup asks for --config PATH, point it at your VS Code profile's mcp.json and test. Mark anything weird for the issue tracker. (docs/mcp.md)

You installed splinterm-mcp but nothing agent-shaped can connect, and the adapter binary isn't where expected

Fix: The adapter identity is exact: setup resolves the installed adapter next to the splinterm you run (/usr/bin/splinterm-mcp for the package). A user-local build in ~/.cargo/bin is offered only short-duration grants, and a raw Nix store path never gets "Always" and dies on upgrade/GC. If in doubt, splinterm mcp setup --dry-run shows the exact adapter path and identity it would use. (docs/mcp.md)

Pairs well with / If you hate this, try

Pairs well with

  • splinterm (required — the adapter is a split package of its automation surface; see the Splinterm guide)
  • herdr (dedicated Omarchy agent-status watcher; Splinterm's agent-status display covers the basics, herdr is the specialist)
  • claude-code / openai-codex-bin (the hosts the adapter plugs into)

If you hate this, try

  • tmux control mode (tmux -CC / control mode scripts) — the DIY route to letting scripts drive a terminal, with none of the consent/policy machinery (and none of the safety)
  • paste into your agent host's own terminal — zero integration, zero risk

If the idea of agents in your shell makes you itchy, this whole package is skippable — Splinterm works fine as a human terminal without it.

splinterm-mcp is a free alternative to Warp's AI blocks ($15/mo) and cloud agent environments

splinterm-mcp is a free alternative to Warp's AI blocks ($15/mo) and cloud agent environments. What you give up: Warp's polished UI and cloud sync. What you keep: local-only control, an audit trail, and zero subscription — agents reach your persistent local sessions, but access is consent-gated by default, scoped to exact executable identity, and revocable per workspace. For the Omarchy user who wants coding agents in the terminal without the cloud, this is the native path.

How to switch from Warp AI / a cloud agent setup (~15 minutes)

  1. Export from Warp: nothing to export — your agent context lives in Warp's cloud, and the migration is to a consent-gated local model anyway. Note which projects you ran agents in.
  2. Install both packages: omarchy pkg add splinterm, then omarchy pkg add splinterm-mcp. Remember: installing grants nothing.
  3. Plug in your host: splinterm mcp setup claude-code (or codex), start a new host session, and grant access per workspace when the agent first asks — choose the narrowest access level and duration that gets the job done.
  4. What doesn't transfer: Warp's polished agent UI and cloud-synced context. What you gain: local-only control, per-workspace consent, and grants you can revoke with splinterm access revoke.

Frequently asked questions

Does splinterm-mcp work on Omarchy?

Yes — it's an official Omarchy package (0.1.1-1) from the same repo as Splinterm. The validated target is x86_64 Omarchy/Arch with native Wayland.

Is splinterm-mcp free?

Yes, MIT-licensed open source, part of the splinterm repository. No paid tier.

Does installing it give my agents access to my terminal?

No — and that's the point. Installing the package, or running splinterm mcp setup, grants nothing. The daemon denies every adapter operation until you answer the consent prompt (or write an exact policy). Terminal output remains untrusted data and can never grant authority.

Which agent hosts does it support?

Claude Code, Codex, and VS Code via splinterm mcp setup <host>. The VS Code entry form is upstream-unverified — test before trusting it.

How do I completely remove it?

Remove the host entry with splinterm mcp remove claude-code (or whichever host), revoke grants with splinterm access revoke, then omarchy pkg drop splinterm-mcp. Removing the host entry alone revokes nothing — do both steps.

Can agents report what they're doing, like herdr?

Splinterm 0.2 (on main, accepted in the Omarchy VM, unreleased) adds explicit agent-status reporting: agents self-report working / needs_input / done / error / idle, shown as Explorer icons and Dojo tab badges. On the stable 0.1.1 package, watch the release notes for 0.2 — or run herdr alongside for status watching now.

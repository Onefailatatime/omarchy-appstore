NVIDIA open modules, EEVDF kernel, on Omarchy

linux-omarchy-eevdf-nvidia-open is NVIDIA’s open kernel modules (driver 615.78.08), prebuilt for Omarchy’s EEVDF kernel flavor — the driver half of the NVIDIA stack for people who boot linux-omarchy-eevdf instead of the default kernel. It’s for Omarchy users with a Turing-or-newer NVIDIA GPU (GTX 16-series, RTX 20-series and up) running the EEVDF kernel.

TL;DR

omarchy pkg add linux-omarchy-eevdf-nvidia-open
sudo reboot
# at the bootloader, pick the linux-omarchy-eevdf entry
nvidia-smi   # after reboot: should list your GPU and driver 615.78.08

Takes ~2 minutes (10.3 MB download). Who this is for: people with an NVIDIA GPU who run the EEVDF kernel flavor — plain upstream EEVDF scheduling, no BORE/ADIOS patches. If you run the default kernel, you need linux-omarchy-nvidia-open instead; MuQSS users need linux-omarchy-muqss-nvidia-open. The modules only load into the exact kernel they were built against. If you have an AMD or Intel GPU, you don’t need this package at all. If your NVIDIA card is older than Turing (GTX 10-series, 9-series, or older), these modules will not work for you — see Common issues.

Getting started (10 minutes — includes a reboot)

1. Check your GPU is supported.

The open kernel modules work on Turing GPUs and later — GTX 16-series, RTX 20-series and everything newer (per NVIDIA’s own compatibility list). Find your card with:

lspci | grep -i nvidia

If it says GTX 1060, 1070, 1080, or anything older, stop: the open modules don’t support it, and you want the proprietary-module path (nvidia-580xx-dkms in the store) instead. If it says RTX 2060 or newer, or GTX 1650/1660, you’re good.

2. Check which kernel you’re running.

This package is built for the EEVDF kernel flavor only:

uname -r

You should see a release string ending in -omarchy-eevdf (e.g. 7.2.15-4-omarchy-eevdf). If it ends in plain -omarchy or -omarchy-muqss, install the matching -nvidia-open package for that flavor instead — same guide, different package name. If you haven’t installed the EEVDF kernel at all yet, install it first (omarchy pkg add linux-omarchy-eevdf — see the EEVDF kernel guide) and boot into it before adding the NVIDIA modules.

3. Install.

omarchy pkg add linux-omarchy-eevdf-nvidia-open. It pulls in the matching kernel (linux-omarchy-eevdf 7.2.15-4) and the matching user-space driver (nvidia-utils 615.78.08) as dependencies — the kernel modules and the user-space driver must be the same version, and Omarchy pins them together. The point of this package: the modules ship prebuilt inside the kernel recipe, so a kernel update never leaves you compiling modules through DKMS. The PKGBUILD comment says it plainly: the modules are built in the kernel recipe “so every kernel lands with modules for it and nobody compiles them through DKMS on a kernel update.”

4. Boot the eevdf entry and verify.

Reboot, pick the eevdf kernel entry in the bootloader (Omarchy uses limine — your default kernel stays installed and stays the default, the eevdf entry is an addition), then check three things:

uname -r                    # should end in -omarchy-eevdf
nvidia-smi                  # lists your GPU, driver version 615.78.08, VRAM, temperature
lsmod | grep nvidia         # nvidia, nvidia_modeset, nvidia_uvm, nvidia_drm loaded
modinfo nvidia | grep version  # version: 615.78.08

nvidia-smi succeeding is the real test — it proves the kernel modules loaded and the user-space driver is talking to the card. The modules live in /usr/lib/modules/<kernel-release>/extramodules, signed with the same key the kernel build signed its own modules with. If uname -r still shows the default kernel, you booted the wrong entry — the NVIDIA modules for eevdf won’t load under it, and neither will the default kernel’s modules under eevdf.

5. The 3 things you need to know:

  • This is one half of the driver. The kernel modules in this package are the half that lives in the kernel. The other half — nvidia-utils (the nvidia-smi binary, the GL/Vulkan libraries, the X/Wayland driver pieces) — is a dependency that installs automatically. If you ever update one without the other, the driver breaks; always update the whole system together (omarchy update), never the kernel modules alone.
  • It conflicts with the DKMS build. This package declares conflicts=(nvidia-open-dkms). That’s the same open modules built from source via DKMS — the package for people on kernels other than Omarchy’s three flavors. If you have nvidia-open-dkms installed, pacman will make you remove it first. On an Omarchy kernel, prefer the prebuilt package: no compile wait on every kernel update.
  • It only works with its kernel. The modules are built against kernel 7.2.15-4 eevdf exactly. Boot a different kernel flavor and they won’t load — that’s by design, and it’s why there are three sibling packages (default, EEVDF, MuQSS), one per kernel flavor. The EEVDF kernel itself is the “control group” kernel: same Omarchy patchset as the default, plain EEVDF scheduling instead of BORE/ADIOS.

Common issues & fixes

Your GPU is a GTX 10-series (Pascal) or older, and the modules won’t load — or nvidia-smi says no devices found

Expected, not a bug: NVIDIA’s open kernel modules support Turing GPUs and later only (GTX 16-series, RTX 20-series and up).

Fix: Older cards need the proprietary kernel modules instead — in the store that’s nvidia-580xx-dkms (driver 580 series, proprietary modules). (NVIDIA open-gpu-kernel-modules README — “Compatible GPUs”)

You installed the wrong flavor — nvidia-smi fails, or the modules don’t load, after booting a different kernel

Each -nvidia-open package is pinned to its kernel (depends on the exact kernel package and version).

Fix: Install the one matching the kernel you actually boot: linux-omarchy-eevdf-nvidia-open for -omarchy-eevdf, linux-omarchy-nvidia-open for -omarchy, linux-omarchy-muqss-nvidia-open for -omarchy-muqss. Check uname -r first, then install the matching package. (PKGBUILD depends, read 2026-11-23; on-machine confirmation pending.)

You installed the package but uname -r still shows the default kernel after reboot

Installing a kernel package only adds a boot entry — it doesn’t change which entry boots by default.

Fix: Reboot, open the bootloader menu (Omarchy uses limine), and select the eevdf entry explicitly. If you want it as the default, change the default in the limine configuration (verify exact steps on-machine). General Arch behavior, not package-specific — same as the EEVDF kernel guide.

Pacman refuses to install, complaining about a conflict with nvidia-open-dkms

The two packages are mutually exclusive by design (conflicts=(nvidia-open-dkms) in the PKGBUILD).

Fix: Remove the DKMS package first — omarchy pkg drop nvidia-open-dkms — then install the prebuilt one. The DKMS package exists for kernels other than Omarchy’s three flavors; on an Omarchy kernel you don’t need it. (nvidia-open-dkms README)

After a partial update, the driver is broken — nvidia-smi fails with a version mismatch, or the desktop won’t start

The kernel modules and nvidia-utils must be the same driver version (615.78.08), and Omarchy keeps them in lockstep deliberately (“Keep this version in step with nvidia-utils” — PKGBUILD header comment). A partial upgrade that updates one and not the other breaks the pair.

Fix: Update the whole system: omarchy update, then reboot. Don’t pin or hold one of the two packages.

Black screen or a Wayland session that won’t start after installing the driver

General NVIDIA-on-Arch practice, not verified for driver 615 on Omarchy — see the checklist. The usual suspects: the nvidia_drm module needs modesetting enabled for Wayland compositors (Hyprland included).

Fix: Omarchy’s 580-series utils package enables atomic kernel modesetting by default via a patch, and the same expectation applies to the 615 series — confirm on-machine whether any nvidia_drm.modeset=1 / fbdev=1 kernel parameter is still needed. If you hit a black screen, boot into a TTY (Ctrl+Alt+F2), check journalctl -b -p err and dmesg | grep -i nvidia for the actual error before changing parameters.

Suspend/resume misbehaves on an NVIDIA laptop — the machine won’t wake, or the GPU stays powered

General NVIDIA practice, unverified for this driver version on Omarchy. The NVIDIA suspend/resume path needs the nvidia-suspend/nvidia-resume services plus NVreg_PreserveVideoMemoryAllocations=1; Omarchy’s 580-series utils ship an nvidia-sleep.conf for this.

Fix: If suspend breaks after installing, check whether the equivalent config exists for the 615 series and report what you find — the checklist covers confirming this on-machine.

Pairs well with / If you hate this, try

Pairs well with

  • The EEVDF kernel itself (linux-omarchy-eevdf) — this package is meaningless without it; the kernel guide covers the scheduler A/B test that is the whole reason to run this flavor. For actually using the GPU: LM Studio (in the store) for local AI, or any game via Steam/Heroic. For monitoring, nvidia-smi is built in; nvtop gives you a live htop-style GPU view.

If you hate this, try

  • nvidia-580xx-dkms — the proprietary kernel modules for the older 580 driver series, built via DKMS. Same GPU, closed-source kernel modules, different trade-offs (broader legacy support, no open code). Or Nouveau, the community open-source driver: fully open, no NVIDIA code at all, but no CUDA and much weaker 3D performance — a principled choice, not a practical one for gaming or AI work.

NVIDIA’s open modules cost $0 — the win is openness, not price

There is no paid driver to replace here — every NVIDIA driver on Linux is free of charge. The honest angle is openness, not price: these are NVIDIA’s open kernel modules (MIT/GPL-2.0) instead of the proprietary ones, which means the kernel-side code is auditable and ships prebuilt in lockstep with the kernel. What you give up vs the proprietary modules: support for pre-Turing cards, and a few edge features NVIDIA documents as open-module limitations. What you keep: the same GPU, the same performance for gaming and CUDA, and a driver that never needs a DKMS rebuild after a kernel update. The fully-open alternative is Nouveau — also free, but without CUDA and with much weaker 3D performance, so it’s a statement, not a substitute.

Frequently asked questions

Do I need this package?

Only if you have an NVIDIA GPU (Turing or newer) and run the EEVDF kernel flavor. AMD/Intel GPUs don’t need it. If you run the default kernel, install linux-omarchy-nvidia-open instead — the packages are per-flavor.

Which of the three -nvidia-open packages do I install?

Match your kernel: uname -r. Ends in -omarchy-eevdf → this package. Ends in -omarchy → linux-omarchy-nvidia-open. Ends in -omarchy-muqss → linux-omarchy-muqss-nvidia-open. One per kernel flavor, never two at once.

Why is there a separate package per kernel?

Kernel modules load only into the exact kernel they were built against. Omarchy builds the same NVIDIA driver source three times — once per kernel flavor — and ships each as its own package, so a kernel update always lands with matching modules and nobody compiles anything through DKMS.

What is the EEVDF kernel, anyway?

Omarchy’s alternative kernel flavor: the same Omarchy patchset as the default kernel, but with plain upstream EEVDF scheduling instead of the BORE CPU scheduler and ADIOS I/O scheduler. It’s the “control group” kernel for scheduler A/B tests — see the EEVDF kernel guide for the full comparison.

Can I install this alongside nvidia-open-dkms?

No — they conflict. The DKMS package is the same modules built from source, for kernels other than Omarchy’s three. On an Omarchy kernel, use the prebuilt package.

What GPUs does it support?

Turing and later: GTX 16-series, RTX 20/30/40/50-series, and equivalent Quadro/datacenter cards. Pre-Turing cards (GTX 10-series and older) are not supported by the open modules at all — use the proprietary 580-series DKMS package.

What happens on a kernel update?

The matching -nvidia-open package updates with the kernel (same version, same release). No DKMS rebuild, no manual step — that’s the design. A partial update that moves one without the other will break the driver, so always update the full system.

Does it work with Secure Boot?

The modules are signed with the key the kernel build generated and signed the kernel’s own modules with. Whether that satisfies a Secure Boot-enforcing machine is on the on-machine checklist — unconfirmed.

How do I uninstall it?

omarchy pkg drop linux-omarchy-eevdf-nvidia-open. Then reboot. If you were relying on it for your display, have a fallback ready (the open-source Nouveau driver loads in its absence, or reinstall before rebooting).

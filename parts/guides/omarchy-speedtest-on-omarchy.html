omarchy-speedtest on Omarchy

omarchy-speedtest is Omarchy's own network speed test client: it measures your download or upload speed against speed.omarchy.org and powers the omarchy network speedtest command and the speed test panel — no browser, no account, no ads.

TL;DR

omarchy pkg add omarchy-speedtest

Takes ~2 minutes.

The store listing reports a 2.9 MB download / 6.8 MB installed. MIT-licensed open source, free forever, no paid tier, no account. Version 0.2.1-1 at guide-staging time (Oct 2026).

Getting started (5 minutes)

1. The mental model — this is a component, not an app you open.

Most Omarchy tools in this guide series are things you launch. This one is different: it is the engine behind a feature you already have. omarchy network speedtest and the speed test panel run it for you. The direct omarchy-speedtest command exists for scripting, debugging, and comparing numbers — you only reach for it when the panel's number surprises you and you want the raw output. If you just want to know "how fast is my connection right now," use the panel, not the CLI.

2. Install and run your first test.

omarchy pkg add omarchy-speedtest   # install
omarchy network speedtest           # the normal way: Omarchy's own command/panel path

For the raw CLI (per the README):

omarchy-speedtest down        # download test: streaming Mbps, final rate last
omarchy-speedtest up          # upload test
omarchy-speedtest down --json # one machine-readable record, for scripts

Without --json, the README says it prints the running rate in Mbps about four times a second and the final rate last, one number per line. With --json, it prints exactly one record:

{"bytes":577238143,"seconds":5,"mbps":923.58,"connections":8}

3. The three things everyone needs to know:

  • It tests against one server: speed.omarchy.org. That is a feature, not a bug — the same endpoint every time means your numbers are comparable week to week. But it also means the number is "your speed to Omarchy's server," not "your speed to the nearest Ookla server" or "your speed to Netflix." If speedtest.net says 900 and this says 600, neither is lying; they measured different paths. Compare omarchy-speedtest against itself over time, not against other testers in the same minute.
  • A test is five seconds, eight connections. Per the README, it opens eight persistent HTTP/1.1 connections, warms up (connection setup and warm-up sit outside the measurement), grows each request until it takes 250 ms, then measures a five-second window and counts only payload bytes. That design is why the number is stable: it is not a single burst, and a slow connection joining late cannot stretch the clock. The flip side: a five-second test will not catch the slow fade of a long download or a connection that degrades after a minute.
  • It reports speed only — no ping, no jitter. The README documents download and upload in Mbps and nothing else. If you need latency (ping/jitter) for gaming or calls, pair it with a ping test (ping to your router, then to a public host) — do not expect a latency figure out of this tool, and do not read one into the JSON record. The record carries bytes, seconds, mbps, and connections only.

4. Scripting it (the --json payoff).

The single-record JSON output is the whole reason the CLI exists alongside the panel. A one-liner logs a timestamped result you can graph later:

omarchy-speedtest down --json >> ~/speedtest.log

Exit codes make scripts reliable: 0 means a result, 1 means the test failed, 2 means a usage error (bad argument). Check the code before trusting the output — a failed test prints no result record, it exits 1.

5. Config location.

No config file is documented. Behavior is driven by the command (down/up, --json) and three environment variables documented in the README:

  • OMARCHY_SPEEDTEST_PARENT_PID — the launcher's parent, set by omarchy-network-speedtest; the panel uses this so a closed panel never leaves transfers running
  • OMARCHY_SPEEDTEST_URL — another compatible service, for development
  • OMARCHY_SPEEDTEST_CONNECTIONS — 1 to 16 connections instead of 8, for comparisons

Do not set OMARCHY_SPEEDTEST_URL for normal use — it exists so developers can point the client at a test service. Pointing it anywhere else changes what you are measuring.

Common issues & fixes

The repo was created Oct 26, 2026 — the day this guide was drafted — so there is no issue tracker history to mine, and nothing below is presented as a user-reported bug. Every item is a behavior documented in the README, with the practical consequence spelled out. Anything not in the README is marked unverified.

My number is much lower than speedtest.net / fast.com showed.

Expected, not a fault — different servers, different paths. This client measures only against speed.omarchy.org, over eight connections in a five-second window, counting payload bytes only. A browser test picks a nearby server, often with a different connection count and duration, and may count differently. Re-run the Omarchy test twice, then compare it with your own earlier Omarchy results, not with another tester's number. If the Omarchy number itself has collapsed versus last week, that is the signal worth chasing (cable, Wi-Fi band, VPN — see below). Unverified on Omarchy: whether the panel surfaces the server location or any per-connection detail.

The test fails outright, or errors about a slow first byte.

Documented behavior: a first byte later than the three-second drain allowance ends the run with an error saying so. In practice that means the client could not get any payload moving in time — the link was stalled, the server was unreachable, or the connection was so slow it never started. Check the obvious first: are you actually online, is a VPN or proxy in the way, is another download saturating the link? Then re-run. If it fails consistently while the browser works fine, that is a real bug report for the repo — note the exit code (1 = test failed) and the exact error text. Unverified: the exact wording of the error on Omarchy.

Upload numbers look odd behind a VPN or HTTP proxy.

Documented measurement difference. On Linux without a proxy, uploads count what the server's TCP stack acknowledged during the window (tcpi_bytes_acked from TCP_INFO). Through an HTTP proxy, those acknowledgements say nothing about the service, so uploads instead count confirmed requests — an acknowledgement does not prove the body arrived, but the next answered request on the same connection does, and the clock runs until the last one answers. Same tool, different counting method, so proxy and non-proxy upload numbers are not strictly comparable. If you need a clean number, test with the VPN/proxy off, then with it on, and label which is which.

I ran the CLI directly and nothing is on my PATH / the panel closed and the test kept going (or stopped).

Two documented details to check. First, the README says Omarchy installs the client as /usr/lib/omarchy/speedtest — it is a component the panel launches, so the bare omarchy-speedtest name may not be on your PATH the way a normal app binary is; the supported front door is omarchy network speedtest and the panel. Second, the client is deliberately tied to its parent on Linux: it asks for SIGTERM when its parent exits and exits if its parent is no longer the process in OMARCHY_SPEEDTEST_PARENT_PID, so a closed panel never leaves transfers running. If a direct CLI run dies when you close its terminal, that is the parent-death behavior working as designed, not a crash. Unverified: the exact PATH situation on a fresh Omarchy install — confirm before telling anyone to type the bare command.

I want a longer test, or fewer/more connections, to compare with another tool.

You can change the connection count, but not the window. Set OMARCHY_SPEEDTEST_CONNECTIONS to a value from 1 to 16 for comparisons (default 8). There is no documented flag for a longer measurement window — the five-second window is part of the design. If you need a sustained-throughput picture (does the link hold up for a minute?), this is the wrong tool for that question; use a long download or iperf3 against your own server instead, and use omarchy-speedtest for the quick comparable number.

Pairs well with / If you hate this, try

Pairs well with

  • the Omarchy speed test panel itself (the normal front end for this client)
  • ping (for the latency/jitter numbers this tool deliberately does not report)
  • a bar network widget such as omarchy-net-speed (live up/down rates in the bar — current throughput, not a benchmark; a different question from a speed test)

If you hate this, try

  • Ookla's speedtest CLI (the speedtest.net backend, nearest-server selection, includes ping — but a third-party server choice and a separate install)
  • speedtest-cli (the classic Python client, same Ookla backend, widely packaged)
  • fast / fast-cli (Netflix's backend — good for "is my ISP throttling video?" specifically, bad as a general benchmark)

None of these are in the Omarchy store listing for this app; they answer different questions, which is the point.

Free alternative to speedtest.net in a browser (free, but ad- and tracker-heavy)

What you give up: the nearest-server choice, ping/jitter figures, and the familiar web UI. What you keep: the one number that matters (download/upload Mbps), in a five-second terminal run with a JSON record you can log — no browser tab, no ads, no account, no cookies.

Honesty note: speedtest.net itself costs nothing, so this is not a money-saving swap — it is a cleanliness and repeatability swap. The honest pitch is "the same question, asked the same way every time, with output you can script," not "free instead of paid." And the migration is trivial: there is nothing to export. Run the Omarchy test once, write the number down, and that is your new baseline; run it again next week and compare.

How to switch from speedtest.net (~2 minutes)

  1. Export from speedtest.net: nothing to export — your history there stays there.
  2. Import into omarchy-speedtest: nothing to import. Run omarchy network speedtest once and write the number down — that is your new baseline.
  3. What doesn't transfer: nearest-server selection, ping/jitter figures, and your speedtest.net history.
  4. Time estimate: ~2 minutes plus the 2.9 MB install.

Frequently asked questions

Does omarchy-speedtest work on Omarchy?

Yes — it is Omarchy's own client, built for speed.omarchy.org, and it is what omarchy network speedtest and the speed test panel run. Install with omarchy pkg add omarchy-speedtest.

Is omarchy-speedtest free?

Yes. MIT-licensed open source. No paid tier, no account, no ads.

How do I run a speed test the normal way?

Use omarchy network speedtest or the speed test panel. The raw omarchy-speedtest down|up CLI is for scripting and debugging, and per the README the binary lives at /usr/lib/omarchy/speedtest.

What does a test measure?

Download or upload speed in Mbps against speed.omarchy.org, over eight connections in a five-second window, counting payload bytes only. It does not report ping or jitter.

Why does my number differ from speedtest.net?

Different server, different path, different method. This client always tests against speed.omarchy.org; browser tests pick a nearby server. Compare omarchy-speedtest with itself over time.

Can I use it in a script?

Yes: omarchy-speedtest down --json prints one JSON record (bytes, seconds, mbps, connections). Exit 0 = result, 1 = test failed, 2 = usage error.

Can I test against a different server?

Only via the OMARCHY_SPEEDTEST_URL environment variable, which the README documents for development. For normal use, leave it alone — changing the server changes what you are measuring.

Does it work through a VPN or proxy?

It runs, but the upload counting method changes through an HTTP proxy (confirmed requests instead of TCP acknowledgements on Linux), so proxy and non-proxy upload numbers are not strictly comparable.

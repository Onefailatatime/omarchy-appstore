Splinterm on Omarchy

Splinterm is a persistent Wayland terminal for Omarchy where your shells keep running even after you close the window — a splinterd daemon owns sessions, layouts, and terminal state, so detaching is safe and your work is still there when you come back.

TL;DR

omarchy pkg add splinterm

Install splinterm on Omarchy with one command. It takes ~2 minutes. MIT-licensed open source, free forever, no paid tier. Guide drafted against stable v0.1.1 (Omarchy package 0.1.1-1; store listing reports 8.4 MB).

One caution from upstream: the AUR packages (splinterm-bin, splinterm) are prerelease-capable channels, not stable-only — they can advance to release candidates. The Omarchy package (splinterm, version 0.1.1-1) tracks the stable release. Prefer the Omarchy package unless you want to test prereleases.

Getting started (5 minutes)

1. First launch.

Launch Splinterm from the app launcher or run splinterm in a terminal. You get an ordinary-looking terminal window — the magic is invisible: this window is a disposable view into splinterd, the daemon that actually owns your shell. Close the window and the shell keeps running.

2. Wire it into Omarchy (recommended).

Install does NOT change your default terminal or touch Omarchy/Hyprland config. Opt in explicitly:

splinterm integration omarchy enable

This sets Splinterm as your default terminal, tags it as a terminal so Omarchy treats Super+C correctly (until then, universal Super+C sends Ctrl+C — interrupt), and hooks up theme following. It's reversible.

3. The three things you need to know:

  • Windows are views, not owners. The topology is daemon-owned: Lairs (named projects/persistent sessions) contain Dojos (terminal layouts), which contain Splints (shells/panes). A Window is just a native Wayland view onto that topology. Learn this vocabulary once and the whole CLI makes sense.
  • Detaching is the default. Close a window and the work keeps running. Reopen through the Dojo picker: splinterm dojos (pick a running Dojo or start fresh) or splinterm reopen (reopen the last one). Reopening attaches to processes that are still running — exited processes restart only through an explicit restore, never automatically.
  • It's Foot under the hood. The terminal kernel is a Rust translation of Foot (pinned to Foot 1.27.0), so if you've used Foot, behavior is familiar: Sixel, static Kitty images, and inline iTerm2 PNG are supported; full Kitty graphics is not.

5. Config location.

Settings live in ~/.config/splinterm/config.ini (fonts, shell, scrollback, cursor, keymap overlays, theme overrides). On Omarchy, Splinterm reads your active theme's foot.ini and colors.toml and reloads palette changes live, no restart needed. Leave main.font unset and it also follows your fontconfig monospace family live.

Common issues & fixes

All sourced from the project's own docs, troubleshooting page, status doc, and issue tracker. Nothing below was reproduced on Omarchy — confirm each fix on-machine before relying on it.

Upgrading from an old install leaves theme generation broken

e.g. omarchy theme set astra fails with ValueError: missing Omarchy roles: darker_bg, lighter_bg, bright_fg, active_tab_background.

Fix: Open as of 2026-10-20 (issue #183): the theme generator expects older short-form Omarchy role names, and some themes (like Astra) only supply long-form names. The other theme hooks continue, but the Splinterm theme JSON isn't written. No fixed release yet — if you hit it, add your theme to the issue; meanwhile themes with short-form role names generate fine.

yay -S splinterm-bin fails on aarch64 (Asahi/Arch ARM)

Package not available, or a 404 downloading an aarch64 asset.

Fix: Open as of 2026-09-06 (issue #76): the prebuilt package declares arch=('x86_64') only. The stable release is validated for x86_64 Omarchy/Arch with native Wayland under Hyprland — ARM is not a current compatibility promise. On Apple Silicon, use the source-built package (yay -S splinterm) instead of the prebuilt.

A Splinterm window exits immediately with "unauthorized"

Fix: Per the troubleshooting page: the trusted client must be the packaged /usr/bin/splinterm adjacent to the running /usr/bin/splinterd — a user-local splinterm earlier in PATH does not match the daemon's trusted-UI identity. Check command -v splinterm resolves to /usr/bin/splinterm, that client and daemon come from the same package build, and that old windows were reopened after any upgrade.

Daemon restarted after a heavy workload and sessions are gone

Fix: Per the troubleshooting page: check systemctl --user show splinterd.service -p Result,NRestarts,MemoryCurrent for an out-of-memory result. Terminal workloads run in a separate aggregate slice so they don't share the daemon's budget, but if the daemon itself restarts, restoration is explicit by design — Splinterm never reruns saved commands automatically. Inspect exited topology with splinterm list --all and restore what you need.

A new Splint reports an internal launch failure

Fix: Per the troubleshooting page: the daemon fails closed when it can't place the terminal helper in its exact systemd scope before executing the shell. Check journalctl --user-unit splinterd.service -n 40 --no-pager and systemctl --user status app-splinterm.slice. Do not "fix" it by launching the packaged daemon manually — that removes the package's required-containment contract.

Stopping or upgrading the daemon ends all child processes, and there's no way to upgrade live

Fix: By design, not a bug: 0.1.1 has no live daemon-upgrade handoff. Save your work and always upgrade from a terminal not owned by splinterd (e.g. plain foot or ghostty), then reopen Splinterm windows. See Packaging for the upgrade and recovery workflow.

Pairs well with / If you hate this, try

Pairs well with

  • splinterm-mcp (the policy-scoped MCP adapter that lets coding agents reach your sessions safely — separate package; see the Splinterm-MCP guide)
  • herdr (Omarchy's agent-status watcher, for the same automation crowd)
  • tmog-bin (if you like multiple terminal front-ends on the Omarchy store)

If you hate this, try

  • ghostty (Omarchy's default-feel GPU terminal, no daemon, no persistence layer)
  • tmux (the classic: persistent sessions with zero new vocabulary, but no native windows or agent interfaces)
  • foot (the pure upstream emulator Splinterm is derived from — minimal, fast, no daemon)

Splinterm is a free alternative to Warp ($15/mo Pro)

Splinterm is a free alternative to Warp ($15/mo Pro). What you give up: Warp's proprietary cloud sync and built-in AI blocks. What you keep: persistent sessions, tabs and panes, command palette, Omarchy theme integration, and an MCP adapter for coding agents that Warp doesn't offer in this form. For the Omarchy user who wants Warp-style workflow features without the subscription or the cloud, Splinterm is the native answer.

How to switch from Warp (~15 minutes)

  1. Export from Warp: Warp keeps settings in its cloud account — per the free-alternative math above, you give up "proprietary cloud sync," so plan on rebuilding your setup fresh rather than importing it. Note down your key bindings and themes if you customized them.
  2. Install Splinterm: On Omarchy: omarchy pkg add splinterm, then run splinterm integration omarchy enable to make it your default terminal with theme following.
  3. Recreate your workflows as Lairs and Dojos: a Lair is your project/session, a Dojo is a layout inside it, a Splint is a shell/pane. Recreate the layouts you lived in with Ctrl+Shift+Enter splits and Ctrl+Shift+D Dojo tabs.
  4. What doesn't transfer: Warp's cloud-synced settings, AI blocks, and any cloud workflows. What you gain in return: daemon-owned persistence (close the window, the work survives) and a local, consent-gated automation surface instead of a cloud service.

Frequently asked questions

Does Splinterm work on Omarchy?

Yes — it's designed first for Omarchy. The stable release is validated on x86_64 Omarchy/Arch with native Wayland under Hyprland. The Omarchy package ships version 0.1.1-1.

Is Splinterm free?

Yes, MIT-licensed open source. No paid tier, no trial, no feature gates. There's an optional Ko-fi link to support the maintainer.

Do I need to learn new vocabulary (Lair, Dojo, Splint)?

To get real value out of persistence, yes — it's the core model. A Lair is your project/session, a Dojo is a layout inside it, a Splint is an individual shell/pane. It maps roughly to tmux's session/window/pane, so tmux users will adapt in minutes.

What happens when I close a Splinterm window?

Nothing bad — by default, unnamed graphical terminals are persistent. The window detaches; the shells keep running. Reopen with splinterm reopen or pick from splinterm dojos.

Does it change my default terminal or Hyprland config on install?

No. Installation changes nothing about defaults; run splinterm integration omarchy enable to opt into the complete Omarchy integration (reversible).

Can coding agents use my Splinterm sessions?

Through the bounded automation surface, yes — JSON/NDJSON CLI, SSH stdio relay, or the MCP adapter (splinterm-mcp, separate package). Machine clients never inherit human graphical authority, and terminal output is treated as untrusted data. See the Splinterm-MCP guide for the safe path.
